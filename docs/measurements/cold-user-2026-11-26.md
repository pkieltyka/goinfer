# Cold-user run: goinfer v0.6.9 on Linux x86_64 (CPU, cgo-free), 2026-11-26

## Run metadata, contamination, and scope

- **Target release:** `v0.6.9` (tag commit `a1333cf2b78d`, published `2026-11-26T13:43:13Z` on `github.com/pkieltyka/goinfer`)
- **Date & elapsed window:** `2026-11-26`, `16:17:22-05:00` to `16:28:00-05:00` (~10.6 minutes total wall across all phases; inside the 25-minute protocol box)
- **Host hardware:** Linux x86_64 laptop — Intel Core Ultra 7 255H (16 cores / 16 threads, detected CPU kernels `[avx2 f16c popcnt]`), 62.3 GiB host RAM (`~38.6–40.4 GiB` available), 8.0 GiB swap, NVIDIA GeForce RTX 5060 Laptop GPU (8,151 MiB — **unused**; `CUDA_VISIBLE_DEVICES=""` and `--backend cpu` throughout), NixOS Linux kernel `6.18.63`, Go `go1.27.3 linux/amd64`.
- **Execution isolation:** Fresh out-of-tree scratch directory (`<scratch>/cold-user/`) with isolated `HOME`, `XDG_CACHE_HOME`, `GOMODCACHE`, and `GOCACHE`; `GOWORK=off`, `CGO_ENABLED=0`, `GOTOOLCHAIN=local`, `GOPROXY=https://proxy.golang.org`, `GOSUMDB=sum.golang.org`. All phases ran under the host timing lock (`~/.goinfer-timing.lock`). Only published `v0.6.9` GitHub release downloads, the published `v0.6.9` README, `--help`/`go doc` output, and published Go proxy modules were used — zero local source checkout was compiled or executed.
- **Contamination disclosure (per Run 2 amendment):** **Contaminated (prior-contact session).** The executing session had prior repository read access and pre-existing knowledge of `goinfer` conventions and docs. Commands, friction, and dead ends were nevertheless executed strictly from published `v0.6.9` artifacts in the isolated scratch tree and recorded verbatim.
- **Device scope:** CPU-only / cgo-free Linux x86_64 execution. No CUDA device test and no Apple Silicon / Metal device test were run (macOS `darwin/arm64` `backend/metal@v0.6.9` was verified by cgo-free cross-compilation only).

## Detailed scenario results

### Scenario A — Try it (nothing to first answer, download vs run legs split)

1. **Download leg:**
   - `goinfer-chat-linux-amd64` (`40.9 MB`): `2.800 s`, SHA-256 matched `checksums.txt`, SLSA v1 attestation verified.
   - `goinfer-chat-linux-amd64 pull qwen2.5-coder-0.5b` (`Qwen/Qwen2.5-Coder-0.5B-Instruct-GGUF:q4_k_m`, `468.6 MiB`): **`27.575 s`** (`~17 MiB/s`, SHA-256 verified).
   - `goinfer-chat-linux-amd64 fit <gguf>` reported `cpu RESIDENT @ int4: dense 0.44 GiB + KV@16384 0.38 GiB fits 38.81 GiB free`.
2. **Run leg (CPU, greedy `--temp 0 --max 64`, prompt `"What is the capital of France? Answer in one sentence."`):**
   - **Cold launch #1** (includes one-time `.giw` sidecar transcode `qwen2.5-coder-0.5b-instruct-q4_k_m.int4.e4h.cpu-amd64.v17.giw`, `344 MB` in `1 s` — stream `0.6 s`, self-check `0.0 s` — plus `10 ms` model load):

   - **Warm launch #2** (sidecar present, `12 ms` model load):
     - Wall: **`0.686 s`**, max RSS: **`339,128 kB` (`331.2 MiB`)**, rate: **`[7 tok, 14.3 tok/s]`**, output: `The capital of France is Paris.`

## Timestamped friction log (ordered by impact)

1. **`16:17:36` — NixOS `libcuda.so.1` lookup & repetitive stderr during `check --hardware`:** Even on a laptop with an NVIDIA RTX 5060 Laptop GPU, `libcuda.so.1` on NixOS lives under `/run/opengl-driver/lib/libcuda.so.1`, outside goinfer's hardcoded lookup list (`libcuda.so.1`, `/usr/lib/x86_64-linux-gnu/libcuda.so.1`, `/usr/lib/wsl/lib/libcuda.so.1`). In addition, `goinfer-serve check --hardware` printed the full `[resident] BuildResident declined ...` block 4 times on stderr (once per tiny self-test model) even after already probing `cuda: no usable device`.
2. **`16:20:05` & `16:23:30` — `opencode v2.4.1+6f05140` hung before sending any HTTP request (2 attempts):** `goinfer-serve connect opencode -write` worked cleanly and produced a valid `opencode.json` (with the `-fast` alias), yet `opencode run` timed out inside its own `opencode serve --stdio --port 0` subprocess in an isolated `HOME` (note: a separate system `opencode 2.2.4` service was already running on the host). Not attributable to `goinfer-serve` HTTP handling, which never received a request, but a real cold-user friction point when testing `opencode` in a clean environment.
3. **`16:17:36` — Version string mismatch in `goinfer-serve check --hardware`:** `--version` correctly printed `v0.6.9 (a1333cf2b78d)`, whereas `serve check --hardware` printed pseudo-version `v0.0.0-20261126131256-a1333cf2b78d (a1333cf2)`.
4. **`16:21:31` & `16:22:20` — Positional `[url]` vs `--url` flag on `check` and `connect`:** Both `goinfer-serve check` and `goinfer-serve connect <agent>` take the server URL as a positional argument (`check [url]`, `connect <agent> [url]`); passing `--url` exits 2 (usage message is clear and immediately corrects the user).
5. **`16:17:32` — `gh attestation verify` silent when stdout is piped/redirected:** Running the README's exact `gh attestation verify ./goinfer-serve-linux-amd64 --repo pkieltyka/goinfer` under redirected logging exited 0 with empty output; `--format json` was required to capture verifiable SLSA metadata in logs.
6. **`16:27:49` — Second `.giw` sidecar transcode in Scenario C:** `goinfer-chat` defaulted `EmbedInt4=true` on the 0.5B model (`*.int4.e4h.cpu-amd64.v17.giw`, `344 MB`), whereas minimal Go code passing `decoder.Options{Backend: "cpu", Quant: "int4"}` leaves `EmbedInt4=false` and triggers a second one-time sidecar transcode (`*.int4.cpu-amd64.v17.giw`, `459 MB`, `~1 s`).
7. **`16:22:36` & `16:22:55` — Minor `go doc` polish:** `decoder.Load` doc has a spacing typo (`a. gguf file`), and `decoder.Model.Generate` points to `examples/embed/main.go` (actual path in README is `apps/examples/embed/main.go`).
8. **`16:19:50` — System `python3` lacked `openai`:** Host Python had no `openai` package installed; verified via isolated `uv run --with openai` (`openai 3.60.0`) inside the scratch cache.

## Exact protocol limitations of this run

1. **Prior-contact contamination:** Executed by an agent with prior `goinfer` repository context (disclosed per Run 2 amendment), despite strict out-of-tree published-only execution.
2. **No GPU device execution:** CPU-only (`--backend cpu`, `CUDA_VISIBLE_DEVICES=""`) to keep Apple Silicon M4 completely free for device testing; neither Metal nor CUDA kernels executed on GPU hardware (`backend/metal@v0.6.9` was cross-compiled on Linux with `GOOS=darwin GOARCH=arm64 CGO_ENABLED=0`).
3. **Scenario D (bigger than RAM):** Host `62.3 GiB` RAM (`~38 GiB` available) exceeded vetted 20–35B MoE footprints; only `fit` and `--stream-weights` CLI/guard acceptance were exercised, not genuine out-of-RAM paging pressure.
4. **Scenario E (peer control):** No `ollama` or `llama-cli` installed on `PATH`; no peer timing comparison recorded.
5. **Scenario B (`opencode`):** Timed out inside `opencode v2.4.1`'s own stdio subprocess across 2 attempts with 0 HTTP requests sent to `goinfer-serve`.
