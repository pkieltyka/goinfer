# EmbeddingGemma 2 peer protocol

Source review on 2026-11-21. This is an experiment design. It contains no new measured speed or quality result.

## Separate the interfaces

| Lane | Input and output | Question |
| --- | --- | --- |
| Encoder fidelity | Exact prepared token IDs, then full-size vectors | Do numerical differences originate in the graph or in preparation? |
| Warm encoder | Prepared token IDs and an already loaded, resident model | Where does forward latency or index throughput go? |
| Served embedding | Exact same texts and prompts, end-to-end HTTP with matched batching and concurrency | What latency and throughput does a client see? |
| pbrain retrieval | Frozen Markdown corpus, index settings, lexical/hybrid mode, and clock | Did retrieval or abstention change? |

The goinfer CPU model's `Model.Embed` consumes IDs, forwards, mean-pools, and normalizes. The stock `Encoder.EncodeBatchCounted` loops over texts and ignores its concurrency argument. In pbrain, `encoder.Embed` iterates texts, applies app-specific token preparation, then calls `Model.Embed` directly. Consequently a fast path exclusively on goinfer's `Encoder` cannot affect pbrain until the caller uses it. [goinfer model](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/embeddinggemma2/model.go) [goinfer encoder](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/embeddinggemma2/encoder.go) [pbrain adapter](https://github.com/pkieltyka/pbrain/blob/b4f8aa1ec5fd389d93f6b64e9bfccb5604b0dd5e/internal/embed/gemma2/gemma2.go)

## Baseline contract

1. Pin source model revision, tokenizer files, converted weights and their digests, engine revisions, exact loader flags, hardware and driver, selected backend and fallback. Verify the model identifier and architecture. EmbeddingGemma 2 is `google/embeddinggemma-2`, backed by Gemma 4. First-generation `google/embeddinggemma-300m` and generative Gemma 2 are separate. Keep BGE-small as a separate workload or retrieval control. [EmbeddingGemma 2 model card](https://huggingface.co/google/embeddinggemma-2) [EmbeddingGemma 300M model card](https://huggingface.co/google/embeddinggemma-300m) [Gemma 2 Transformers documentation](https://huggingface.co/docs/transformers/model_doc/gemma2)
2. Compare exact role-prompt bytes, whitespace, Unicode, BOS and EOS, reserved-control-looking literals, attention masks and effective token counts. The Hugging Face reference uses explicit query/document prompts for retrieval. pbrain treats reserved-looking input strings as literal text, frames IDs with BOS and EOS, and truncates within a 2,048-token cap. For long Markdown it can keep a prefix plus part of the passage. The native goinfer encoder instead rejects input over the model's 8,192-token limit. llama.cpp's stock embedding CLI parses special tokens and its BOS/EOS behavior uses GGUF metadata. Therefore, export exact prepared IDs to isolate model parity and independently verify IDs in the intended served endpoint before using that endpoint for peer timing. [Transformers v5.19.0 usage](https://huggingface.co/docs/transformers/v5.19.0/en/model_doc/embedding_gemma2) [pbrain adapter](https://github.com/pkieltyka/pbrain/blob/b4f8aa1ec5fd389d93f6b64e9bfccb5604b0dd5e/internal/embed/gemma2/gemma2.go) [goinfer encoder](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/embeddinggemma2/encoder.go) [Pinned llama.cpp CLI](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/examples/embedding/embedding.cpp)
3. Verify the forward contract with short ordinary inputs, an input crossing the local-attention boundary, and mixed-length batches. EmbeddingGemma 2 uses bidirectional attention, interleaved local and full layers, a per-layer input projection and a learned 768-wide output projection. Pool non-padding rows, including prompt and framing tokens, and normalize. The pinned llama.cpp architecture uses a symmetric window and no-cache attention. Its converter doubles the Hugging Face window parameter to express the full window, so an equal-looking numeric setting in two runtimes is insufficient. A linear projection can commute with mean pooling in real arithmetic, with a separate numerical check needed for accumulation and rounding. Check singleton versus batch, changed values at the window edge, finite output, unit norms, and ordering. [Transformers v5.19.0 architecture](https://huggingface.co/docs/transformers/v5.19.0/en/model_doc/embedding_gemma2) [Pinned llama.cpp model](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/src/models/gemma-embedding2.cpp) [Pinned llama.cpp converter](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/conversion/gemma.py)
4. Start with the full 768-dimensional output. If testing a Matryoshka prefix later, truncate both sides to the same dimensions and normalize afterward. Keep the normalized-vector and per-token/per-layer comparisons distinct. MLX's maintainers reported larger BF16 error in token states than in pooled vectors on their Apple M5 Max validation. Treat close vectors, stable retrieval and bit identity as separate outcomes. [Transformers v5.19.0 Matryoshka guidance](https://huggingface.co/docs/transformers/v5.19.0/en/model_doc/embedding_gemma2) [Pinned MLX-VLM validation](https://raw.githubusercontent.com/Neywa-Labs/mlx-vlm/fec3f50/mlx_vlm/models/embedding_gemma2/README.md)
5. Record source storage dtype, device weight dtype, activation dtype and math mode separately. The pinned Hugging Face config declares BF16. goinfer's CPU loader expands weights to float32. The ggml-org releases supply BF16 and Q8_0 and the converter accepts F32. For a parity-first cross-engine cell, export F32 GGUF from the same HF snapshot and verify the actual tensor types and kernel math mode. A BF16 or Q8_0 deployment can be measured in its own cell, with vector and retrieval checks at that setting. [Pinned HF config](https://huggingface.co/google/embeddinggemma-2/blob/f9972ac22e696a105c482202646979e33e4b5a1e/config.json) [goinfer loader](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/embeddinggemma2/model.go) [Official llama.cpp GGUFs](https://huggingface.co/ggml-org/embeddinggemma-2-GGUF) [Pinned converter flags](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/convert_hf_to_gguf.py)

## Timing design

Start with warm latency at batch one on real short pbrain queries and throughput for ordered Markdown passages with a known token-count distribution. Include a mixed-length batch and a long prepared passage, with observed lengths and total tokens in the log. Sketch candidate cases from the existing attributed pbrain fixtures, then freeze them at a revision before timing. Count actual requests, sequences and tokens, and record both logical batches and device microbatches. For app measurements capture cold process startup/first query, a warm query and index construction as separate outcomes. Track throughput, latency distribution, peak host and device memory and transfers. Record whether unused modality towers are loaded. Keep benchmark endpoints, device, toolchain, weight precision and output formats aligned. [pbrain retrieval fixture](https://github.com/pkieltyka/pbrain/tree/b4f8aa1ec5fd389d93f6b64e9bfccb5604b0dd5e/internal/semantic/calibrate/testdata/retrieval) [llama.cpp embedding CLI source](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/examples/embedding/embedding.cpp) [Transformers text-only loading](https://huggingface.co/docs/transformers/v5.19.0/en/model_doc/embedding_gemma2)

Extend `scripts/bench_peer.py` before a peer timing claim. Its current `run_embed_cell` generates filler texts and uses a CPU goinfer arm and an Ollama arm. The pinned llama.cpp server has a suitable normalized `/v1/embeddings` endpoint, but the harness currently lacks its embedding adapter. Add a distinct EmbeddingGemma 2 workload with fixed payloads, preflight parity, local checkpoint paths, explicit device selection, and same-session interleaving. Evaluate any app-prepared-ID lane as an explicitly different interface. [goinfer peer harness](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/scripts/bench_peer.py) [Pinned llama.cpp server API](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/tools/server/README.md#post-v1embeddings-openai-compatible-embeddings-api)

The verified Linux CUDA peer available on the RTX host is the official llama.cpp `b12613` archive at commit `362ac929749d56e433878585a8506f24968698b4`, CUDA 12.8. Both the binary and runtime archives matched the release digests. Its `--list-devices` selected the RTX PRO 6000 with driver 595.112.07 on 2026-11-21. Treat it as a separate build from the local source reference `e6d624b9a`. Confirm real-model token and vector parity before timing it. [Pinned CUDA release](https://github.com/ggml-org/llama.cpp/releases/tag/b12613)

On the same date, the `e6d624b9a` converter produced an F32 GGUF from Google snapshot `f9972ac22e696a105c482202646979e33e4b5a1e`, SHA-256 `1e61453cc7a9a5583dbd27b2d29a2347574814063347945d6d8e5d3ecbe58dfd`, using CPU PyTorch 2.11.0 and Transformers 5.19.0. The untimed CPU probe and CUDA server both passed on prepared IDs for two queries and four notes. The CUDA server logged 25 of 25 layers offloaded. With flash attention off and per-sequence mean pooling and L2 normalization, the six singleton and two two-document batch requests each took one decode call. The worst CUDA cosine against a native singleton vector was 0.99999999999033. The longest input was 2,655 tokens. Keep this as correctness and physical batch evidence. For timing, compare direct prepared-ID calls with any other direct-call engine and HTTP round trips with another HTTP arm.
