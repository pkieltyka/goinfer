# AMD Linux feasibility

Source snapshot checked 2026-11-21. This note contains source review and proposed tests.

## Device selection before kernel work

At goinfer `e33aa3893`, WebGPU's `New` asks for a high-performance adapter and raises storage-buffer and dispatch limits. Software fallback detection exists for the tests. The bound native library can enumerate Vulkan adapters and expose numeric vendor and device IDs in addition to the graphics API and adapter type. Use this as the basis for explicit selection, with rejection if the requested adapter is absent or ambiguous. Numeric vendor and device IDs identify a model, so an exact physical device selection between two identical cards still needs additional identity or a process-level selector. [goinfer WebGPU context](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/backend/webgpu/internal/kernels/gpu.go) · [Native adapter enumeration](https://github.com/oliverbestmann/webgpu/blob/v1.38.0/wgpu/instance.go) · [Binding adapter info](https://github.com/oliverbestmann/webgpu/blob/v1.38.0/wgpu/adapter.go) · [WebGPU adapter identifiers](https://www.w3.org/TR/2026/CRD-webgpu-20261116/#gpuadapterinfo)

The preceding local investigation identified the Radeon RX 9060 XT as RADV GFX1200, PCI vendor/device `1002:7590`. On this mixed-GPU host, use a process-local RADV manifest override with `VK_DRIVER_FILES` and a PCI-address selector of the form `DRI_PRIME=pci-<address>!`. Mesa documents the exclamation suffix as restricting Vulkan's visible devices to the selected one. Confirm that the test process can resolve the system Vulkan loader and the selected ICD library. A system `vulkaninfo` process can have different dynamic-loader visibility from the Go executable, so verify the identity reported inside the actual test or server. Run filtering as a test setup, without adding a production goinfer environment variable. [Mesa environment variables](https://docs.mesa3d.org/envvars.html#envvar-DRI_PRIME) · [Khronos loader driver discovery and override](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderDriverInterface.md)

The existing WebGPU module's native dependency uses cgo. Reusing it preserves the separate pure-Go root and is the shortest AMD feasibility route for an optional device build. A requirement that the AMD executable itself build with `CGO_ENABLED=0` would require a different binding or backend, with that build verified separately. Go's current Metal module provides the pattern for keeping native GPU calls behind an optional cgo-free Go boundary. [WebGPU native implementation](https://github.com/oliverbestmann/webgpu/blob/v1.38.0/wgpu/instance.go) · [goinfer Metal device binding](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/backend/metal/internal/gpudev/metal.go)

## What to borrow from llama.cpp

- Its pinned EmbeddingGemma 2 graph uses non-causal, cache-free attention and a symmetric window pattern. In the Vulkan backend, physical-device enumeration and visibility can be controlled independently of model graph placement. The operation predicates distinguish supported tensor types and shape conditions before dispatch. This suggests reporting actual operator coverage and checking fallback explicitly in comparisons. [EmbeddingGemma 2 graph](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/src/models/gemma-embedding2.cpp) · [Vulkan backend source](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/ggml/src/ggml-vulkan/ggml-vulkan.cpp)
- Its Vulkan Flash Attention admission checks include head geometry, Q/output types, mask type, and subgroup capabilities. The implementation chooses scalar, cooperative-matrix, or NVIDIA-specific alternatives and checks the shared memory budget for a proposed tile. Shaders are built from GLSL into SPIR-V as a separate build step. The portable takeaway is to dispatch from measured capabilities and tensor shapes, with a baseline path for unsupported shapes. A working AMD Vulkan adapter does not confer support for a particular cooperative-matrix shape or native WebGPU feature. [Vulkan implementation](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/ggml/src/ggml-vulkan/ggml-vulkan.cpp) · [Vulkan shader build](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/ggml/src/ggml-vulkan/CMakeLists.txt) · [Khronos cooperative matrix extension](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_cooperative_matrix.html)
- HIP compiles shared ggml CUDA sources and specialized instances with the HIP toolchain. The pinned tree requires HIP, hipBLAS and rocBLAS and can select an AMD compilation target. AMD identifies the RX 9060 XT as `gfx1200`, with compatibility tied to the ROCm release and host stack. Inference for goinfer: use a matched external HIP run as an upper-bound/reference experiment if it becomes useful. An in-process HIP backend would need its own GPU code generation and runtime boundary, including function loading, launches, memory ownership, synchronization and error reporting. NVIDIA PTX cannot provide AMD kernel binaries. [llama.cpp HIP build](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a4b95c6b52f5ca384d70b75581f9821a/ggml/src/ggml-hip/CMakeLists.txt) · [AMD ROCm GPU requirements](https://rocm.docs.amd.com/projects/install-on-linux/en/docs-7.2.2/reference/system-requirements.html)

## Proposed goinfer work

1. **Prove the selected backend.** Run the WebGPU-linked serve hardware self-test and targeted `TestAdapterProbe`, `TestMatmulBT_matchesNaive` or `TestTiled_parity` as appropriate under the isolated process. Require the reported Vulkan adapter to be the discrete Radeon, exclude software adapters, and require tested shader output and readback to pass. For the hardware self-test, record which tiny fixtures actually ran. This validates the generic path that executes those tests. [goinfer adapter probe](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/backend/webgpu/internal/kernels/adapter_probe_test.go) · [goinfer WebGPU compute tests](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/backend/webgpu/internal/kernels/gpu_test.go)
2. **Bring up a float32 encoder.** The current WebGPU module has matrix and resident vision code, and the text encoder seam is used by Metal. Build a small end-to-end path around device-resident weight, scratch and output buffers. Use matrix–matrix kernels and the Metal block attention algorithm as correctness references. The existing per-call host-slice `MatmulBTResident` result would imply a readback after each projection, so reuse device-side scheduling or helper code from the resident tower. Audit the ABI around offsets, binding alignment and padded/ragged rows. [goinfer WebGPU matrix API](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/backend/webgpu/internal/kernels/gpu.go) · [Resident WebGPU vision tower](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/backend/webgpu/internal/kernels/gemma4_vision.go) · [Text accelerator interface](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/embeddinggemma2/accel.go)
3. **Prove model-specific attention.** Exercise grouped-query mapping with both 256- and 512-wide heads, full bidirectional layers, sliding layers with queries at both inclusive window boundaries, and sequence isolation if batching. Use a future token that changes an in-window output and a token one position farther away that does not. Compare layer inputs and the pooled vector against CPU, with actual hardware execution required. The existing WebGPU decoder attention kernels provide reduction and data-layout examples. Their decode/cache semantics cannot be reused without verifying the encoder mask and grouping. [goinfer CPU encoder](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/embeddinggemma2/model.go) · [goinfer WebGPU decoder attention](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/backend/webgpu/internal/kernels/attention.go)
4. **Specialize from a profile.** Check negotiated WebGPU limits and feature availability. Add a device capability probe and a small shader execution check for any use of subgroups or shader f16, then inspect dispatch and memory behavior for short queries and packed document work. WebGPU specifies separate optional `subgroups` and `shader-f16` features. This context currently requests limits and probes the packed integer dot-product shader. Subgroup size, extensions and half behavior must be verified on the selected native binding and driver. Consider direct Vulkan when a demonstrated WebGPU capability or deployment gap dominates. Consider HIP when a matched peer test attributes a material gap to facilities missing from the simpler path. [WebGPU optional features](https://www.w3.org/TR/2026/CRD-webgpu-20261116/#optional-capabilities) · [WGSL subgroup semantics](https://www.w3.org/TR/2026/CRD-WGSL-20260703/) · [goinfer WebGPU context](https://github.com/pkieltyka/goinfer/blob/e33aa3893e51c15af4a5c5c256d40d728bb1b2f0/backend/webgpu/internal/kernels/gpu.go)

No new device tests or benchmarks ran for this research. Adapter identity, actual encoder residency, optional shader execution and a cgo-free AMD distribution are distinct deliverables.
