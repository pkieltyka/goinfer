# CUDA implementation notes for EmbeddingGemma 2

Source survey completed 2026-11-21. The implementation references are goinfer `e33aa3893e51c15af4a5c5c256d40d728bb1b2f0`, llama.cpp `e6d624b9a4b95c6b52f5ca384d70b75581f9821a`, aikit `0bbc048828e3e546fcf280659d9d9f4ef694936d`, and pbrain `b4f8aa1ec5fd389d93f6b64e9bfccb5604b0dd5e`. The experiments below are proposals. This survey produced no device timings.

## Match the graph and the caller first

- The locally cached `google/embeddinggemma-2@f9972ac22e696a105c482202646979e33e4b5a1e` text configuration specifies 24 layers and a 512-wide residual. Four query heads use 256 dimensions and two K/V heads in sliding layers. Four full-attention layers override the head size to 512 and share one K/V head. goinfer treats the 512-token window as an inclusive radius. Its reference applies Q/K/V normalization and Q/K rotary positions, then uses dot-product scale 1.0. A test longer than 513 tokens is needed to exercise an excluded pair in a sliding layer. [Google model](https://huggingface.co/google/embeddinggemma-2) · [goinfer reference implementation](https://github.com/pkieltyka/goinfer/blob/e33aa3893/embeddinggemma2/model.go)
- llama.cpp constructs a non-causal graph with a symmetric window and no persistent K/V cache for the encoder. It projects all per-layer inputs in one matrix multiply, scales by inverse square root of the hidden width, normalizes each per-layer slice, and uses gated per-layer input and the layer scalar. The final linear projection runs on each normalized token row before the general mean-pooling node. Its no-cache attention graph pads the K/V length to a multiple of 256 and constructs full and sliding masks. Sequence IDs and positions determine allowed pairs. [Model graph](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a/src/models/gemma-embedding2.cpp) · [Masks, no-cache attention and pooling](https://github.com/ggml-org/llama.cpp/blob/e6d624b9a/src/llama-graph.cpp)
- goinfer's `Accelerator` returns projected token rows and has a layer inspection path. The Metal implementation demonstrates persistent weights and scratch, host lookup for token IDs, grouped-query blocked attention via QK and PV GEMMs, and cached RoPE tables. Its PLE scale is applied to the uploaded weights. The CPU reference instead scales the GEMM result before normalization, so compare the intermediate tensors and preserve that order for the first CUDA implementation where rounding differs. The existing CUDA tower executor supplies resident upload, GEMM, RMSNorm, rotary operations, activation and reductions. Its own fused attention specializes head sizes 64, 72, and 80, and its aikit image-attention path uses equal head counts and lacks the symmetric local mask contract. Use the CUDA executor and the Metal schedule as implementation guides. [Accelerator](https://github.com/pkieltyka/goinfer/blob/e33aa3893/embeddinggemma2/accel.go) · [Metal encoder](https://github.com/pkieltyka/goinfer/blob/e33aa3893/backend/metal/embeddinggemma2.go) · [CUDA tower operations](https://github.com/pkieltyka/goinfer/blob/e33aa3893/backend/cuda/tower_base.go) · [aikit GPU kernels](https://github.com/pkieltyka/aikit/blob/0bbc048/gpu/vit.cu)
- pbrain prepares ordinary token segments, inserts its own BOS/EOS, truncates long input, and calls `Model().Embed(ids)`. That call follows the CPU implementation even if an accelerator is registered. Add an accelerator-aware prepared-ID seam and wire the pbrain adapter to it without re-tokenizing. Test the pbrain caller's unchanged role prompts, literal control-token treatment, truncation, array order and cancellation behavior. The server has a separate device-selection helper that currently recognizes Metal for this encoder. [pbrain adapter](https://github.com/pkieltyka/pbrain/blob/b4f8aa1/internal/embed/gemma2/gemma2.go) · [Server device selection](https://github.com/pkieltyka/goinfer/blob/e33aa3893/internal/app/serveapp/embeddinggemma2_embedder.go)

## Hardware and kernel references

The RTX PRO 6000 Blackwell family is compute capability 12.0. NVIDIA lists B200/GB200 separately at 10.0. Confirm compilation, feature gates and the actual selected kernel for SM120. Retain the existing driver and embedded PTX deployment boundary. Architecture-specific Blackwell binaries need their targeted hardware. [NVIDIA compute capability matrix](https://developer.nvidia.com/cuda/gpus) · [Blackwell compatibility guide](https://docs.nvidia.com/cuda/blackwell-compatibility-guide/index.html) · [goinfer CUDA module](https://github.com/pkieltyka/goinfer/blob/e33aa3893/backend/cuda/go.mod)

## Experiment order and falsification

| Order | Experiment | Evidence that would stop or redirect it |
| --- | --- | --- |
| 1 | Build opt-in FP32 CUDA single-sequence text through the existing accelerator registry. Put projection and norm weights on the GPU once. Keep the token gather on the host and reuse one bounded scratch set on the device executor. Build attention with blocked FP32 GEMMs and a row mask as in the Metal schedule, preserving Q/K/V head geometries. Keep the projected-row readback and shared host pooling for the parity path. | Exact prepared IDs, per-layer vectors, final normalized vectors, retrieval outcomes and device execution must pass. Distinguish GQA routing faults from window boundary faults by testing both head layouts and long sequences. If profiling attributes little time to K/V expansion or copies, defer moving the token table and gather. |
| 2 | Measure host submission, preprocessing, H2D and D2H, stream synchronization, and GPU time by operation. Assess projected-row readback against device pooling or moving the linear projection after the mean for pooled output. Mean commutes with a linear projection in exact arithmetic, with final normalization after projection. The CPU pool uses float64 accumulation with an epsilon guard. Preserve the row-level path and measure reduction precision changes separately. | A small share of repeat pbrain latency in transfers, projection, or pooling makes this a lower priority. Non-finite outputs, unstable near-zero normalization, or rank/score drift outside the existing fidelity criteria blocks adoption even if bytes fall. |
| 3 | Batch prepared document IDs using concatenated token rows and monotonic segment offsets. Dense projection and MLP can operate on all rows. Attention uses each document's local positions and segment-specific boundaries. Pool each segment independently and restore the original output order. Plan bounded token and workspace budgets, with short queries retaining their own latency path. | Every document must match its singleton output within the chosen fidelity gate, including a document adjacent to a high-signal unrelated sentinel, ragged lengths, mixed short/long inputs and a boundary exactly at the sliding radius. Record pbrain indexing throughput and query latency separately. Park batching if preparation overhead, memory, or mixed workload queuing erases its application-level gain. |
| 4 | Select the next optimization from traces. If host launch gaps dominate on recurrent shapes, compare graph replay with the same unfused computation, including cold capture and cache hits. Use stable scratch addresses, bound the cache, release graphs when storage moves, and exercise a miss on mixed input lengths. If device kernels dominate, compare grouped QKV and gate/up GEMMs or small epilogue fusions in isolation. | Graphs lose if repeated shapes are rare, setup and padding outweigh replay, or tail latency or memory grows. Keep a fusion only when fewer launches or better operand reuse improves the application workload and the numerical/shape gates hold. Profile graph and node timelines separately to avoid bias from instrumentation. |
| 5 | If attention dominates long inputs, try a two-sided online softmax with explicit 256/512 dispatch and segment clipping. Compare to the FP32 blocked path. If projection GEMMs dominate, use a local cuBLASLt reference for the actual shapes and test reduced precision or optional vendor acceleration separately. | Drop a custom attention path if scoring avoided on long inputs is outweighed by register pressure, reload overhead or insufficient occupancy. Require separate short and long workload results. A favorable causal library result or mismatched precision cannot settle an EG2 kernel decision. |

Useful GPU trace columns include kernel family and duration, launch count, CPU enqueue time, stream gaps, synchronization calls, and bytes copied. Record steady-state scratch high-water marks and allocator counters separately. Nsight Systems can trace CUDA driver calls and graph or graph-node granularity. Collect traces to explain results and run the deciding unprofiled workload separately. [Nsight Systems user guide](https://docs.nvidia.com/nsight-systems/UserGuide/)

Use pbrain's pinned reference cases and actual Markdown length distribution. Start with a warmed query, indexing batch, and long sliding-window case, plus distinctly recorded first call and model load. Run within the project timing discipline using the same local checkpoint and the pinned driver. Interleave candidate and unchanged arms for a performance decision. Require the actual backend in the device record, including explicit CUDA selection from the pbrain path. The project peer harness governs comparisons to llama.cpp. [Repository instructions](https://github.com/pkieltyka/goinfer/blob/e33aa3893/CLAUDE.md)
